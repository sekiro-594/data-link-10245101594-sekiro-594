# M1 接口、通信与风险说明

## 问题 1：`raw_states.json` 中的一条数组与“每个目标只保留最新记录”的当前态势表有什么区别？

**回答：**

`raw_states.json` 中的一条数组只表示某个目标在某一时刻的一次状态记录，字段按照固定下标排列，其中可能包含目标编号、呼号、时间、经纬度、高度、速度和航向等信息。同一个目标可以在文件中出现多次，有些可选字段也可能为空。

当前态势表是在多时刻记录的基础上，先按目标分组、按时间排序，再为每个目标保留最新的一条记录。因此原始数组是处理链的输入，当前态势表是经过解析和时序整理后的阶段性结果，两者不能直接等同。

## 问题 2：为什么发送方内部结构不能直接等同于在线传输字节串？

**回答：**

发送方内部结构主要方便程序处理，可以使用字典、整数、浮点数和空值等 Python 数据类型；在线传输时，通信双方需要使用固定格式的字节串，才能知道每个字段位于什么位置、占多少字节以及如何还原。

本实验中，发送端需要按照 TeachingLink 的字段位置、字节序、比例因子和偏置，把内部状态编码成固定 41 字节消息。接收端不需要知道发送方使用了什么内部数据结构，只需要按照同一协议进行解码。

## 问题 3：`message_valid`、字段有效性和业务数据质量分别回答什么问题？

**回答：**

这三个概念检查的对象不同：

- `message_valid` 表示整帧是否通过长度、magic、版本、类型、保留位和 checksum 等协议检查。
- 字段有效性表示某个可选字段是否真的携带数据，需要查看对应的有效位；有效位为 0 时，协议中的占位整数不能当成真实值。
- 业务数据质量表示数据虽然能够正常解码，但是否存在位置缺失、延迟、重复或航向越界等问题。

因此，一帧的 `message_valid` 为 true，并不代表其中所有字段都有值，也不代表这条记录没有业务异常。

## 问题 4：为什么字节序、位宽、比例因子、偏置和保留位必须由通信双方共同约定？

**回答：**

这些规则决定了字节串应该怎样解释。如果发送端和接收端采用不同字节序，同一组字节会得到完全不同的整数；位宽不一致会使后续字段位置错位；比例因子或偏置错误会让经纬度、高度、速度等数值产生固定偏差。

保留位也需要统一约定。本实验要求保留位为 0，接收端发现保留位异常时会记录错误，避免把不兼容或格式错误的消息继续传给后续模块。我还使用 `roundtrip_report.csv` 检查编码后再解码的数值误差是否在允许范围内。

## 问题 5：CSV 与 SQLite 在本实践中分别承担什么角色？为什么 SQLite 不是必做前置条件？

**回答：**

CSV 用来保存每个阶段的结构化结果，能够直接打开查看，也方便后续模块重新读取和对照。SQLite 更适合练习持久化和条件查询，本实验把多时刻解码记录写入了 `states.db`。

主流程中的航迹、当前态势、语义映射和质量检查都可以直接读取 CSV 完成，所以 SQLite 是选做的补充存储方式，而不是运行 M2-M5 的必做前置条件。

## 问题 6：字段缺失、接口延迟、消息损坏、量化误差和存储失败会造成什么影响？应如何处理？

**回答：**

| 可能出现的问题 | 可能造成的影响 | 本实验中的处理方法 |
|---|---|---|
| 可选字段缺失 | 可能把协议占位的 0 误认为真实数据 | 先检查有效位，无效字段解码为 null |
| 数据到达较晚 | 当前态势可能已经过时 | 将记录时间与批次时间比较，超过阈值就告警 |
| 帧长度或 checksum 错误 | 解码出的字段可能不可信 | 将该帧标记为无效，并记录错误类型 |
| 字节序、比例或偏置写错 | 数值可能产生固定偏差，严重时无法正确解析 | 对照协议说明，并使用回环报告检查误差 |
| 定点量化误差 | 编码再解码的值与原值存在小范围差异 | 根据比例因子计算允许误差，并逐字段检查 |
| 保留位不为 0 | 可能表示格式不兼容或编码错误 | 拒绝该帧并记录 `RESERVED_BITS_ERROR` |
| 同一目标、同一时间重复 | 航迹条数和统计结果会被放大 | 使用 `target_id + timestamp` 联合键检查 |
| 文件或数据库写入失败 | 后续模块无法读取上一步结果 | 各阶段分别保存文件，SQLite 写入使用事务并在失败时回滚 |

通过 M1 的整理，我把外部原始数据、发送方内部状态、传输帧、接收方记录和最终态势区分开了。它们属于不同处理阶段，中间文件不能直接理解成已经完成全部质量检查的最终结果。
